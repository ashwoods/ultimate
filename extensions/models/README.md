Model, thinking, and login, as Pi does them: a model button and a thinking-level button in the composer toolbar, a searchable model picker grouped by provider (availability, login status, context window, thinking, price per million tokens), and a login dialog that drives any pi-ai provider's flow, subscription or API key, with credentials shared with pi in `~/.pi/agent/auth.json`.

Picking a model calls `api.configure({ model })`; the server keeps the thinking level when the model supports it and otherwise clamps it with Pi's `clampThinkingLevel`, and the toolbar shows what it configured. A model whose provider is not logged in opens the login for that provider. The thinking menu offers the model's supported levels (Pi's `getSupportedThinkingLevels`), and Shift+Tab cycles them in Pi's order, like Pi. Commands: `model.pick`, `model.thinking`, `model.thinking.cycle` (Shift+Tab), `auth.login`; the status line's model opens the picker through `model.pick`.

A response that ran on another model or thinking level than the response before it gets a quiet divider above it (`model a → b · thinking high → max`), derived from what each stored response records, so it needs no writes, covers branches and older history, and shows where a change took effect rather than when it was picked. Each response records the thinking level its request asked for (`thinkingLevel`, through this repository's Pi Durable patch); responses from before that compare the level the provider reports (`providerThinkingLevel`), which only some providers do. `switches.ts` derives them.

A conversation whose model's provider has no login here (a removed credential, a moved default) switches when its next run's first input is placed (`fallback.ts`, the patched `beforeInput` hook, so typed inputs, deliveries and queued follow-ups alike). Only certain evidence switches: the availability snapshot lacks the login and a fresh `checkAuth` agrees; a pending, failed or timed-out check keeps the model. It switches to the same model id on another provider with a login, else the model its definition pins (`Profile`, or the label of a branch or lander), else the configured default (`configuredModel` in `lib/agents.ts`), never to whatever model is first. A subscription login (Pi's `isUsingSubscription`; `anthropic` counts as pay-per-token here, since Claude runs on its subscription only through Claude Code) only switches to another subscription: without one it keeps its model and writes a "needs you" entry once. It writes one `models.fallback` entry, `{ from, to?, reason: 'same' | 'pin' | 'default' | 'none' }`, rendered as a card with Pick another and log in; the model reads one line. A run already under way fails once; the watchdog's card then says the provider has no login. New conversations never inherit a model without a login either: branches, standing agents, automation runs and the lander resolve explicit model → usable pin → default, and the root follows the default each time the home opens.

Login is this extension's own: `server.ts` runs Pi's `modelRuntime.login` behind four actions, `login { provider, type }` → `{ flowId }`, `answer { flowId, value }` (an empty answer is an answer), `cancel { flowId }`, and `logout { provider }`. Each flow is shown in `models.login`, a document on the conversation that started it: status, the pending prompt, and the provider's events, never answers, credentials, or provider error details (a failed flow reads `Login failed`). Flows are process-local; one that dies with its process reads cancelled from the next start on. The dialog streams the document with `useDoc` and renders the events (`auth_url` with open and copy, `device_code` with a countdown, `info`, `progress`) and the `text`, `secret`, `select`, and `manual_code` prompts; closing it or the tab cancels a running flow, as does showing another conversation (the document stays with the one that started the flow), configured providers can log out, and a finished login or logout resets that provider's health to unknown (`extensions/health`) and refreshes the model list with `refreshModels()`, which every tab also calls when its window gains focus, for logins in another tab or in pi.

`picker.tsx` is the model picker (its `ModelRow` also lists models in the conversations extension's Summary model picker), `login.tsx` the login dialog, `state.tsx` the shared helpers (the current model, cycling, dialog ids, which provider the login opens on), `server.ts` the login actions and document.
